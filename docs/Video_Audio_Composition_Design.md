# TravelGen 视频合成与跨 Shot 音频实施方案

本方案针对 2026-09-15 的现有 V1 管线：确认实景参考图 → VLM/视觉档案 → Plan/Copywriting → 用户确认文案 → Storyboard → 单 Shot Seedance 视频 → 视频本地转存。目标是把这些片段剪成一条有连续声音、字幕和可复现时间轴的成片。

## 1. 当前状态与必须先修的问题

- `backend/pipeline/pipeline.py` 的文案提示词对 15–120 秒都要求 250–300 字，Storyboard 把模型写出的估计秒数当成真实口播时间。`backend/pipeline/demo.py:parse_script` 只是累加 `paragraph.duration_s`，没有测量音频。
- 已完成样例 `p_20260914_160148_23f31a` 是 15 秒、3 个 Shot（6/5/4 秒），但确认文案的 4 段共有 266 字，被标成 3/5/4/3 秒。这个量级不能靠调快一点语速解决；必须缩短文案并测得真实声音时长，再定镜头时间。
- `backend/pipeline/ark_client.py:transcode_web` 把 Seedance 自动生成的音轨用 `-an` 去掉，避免每镜不同 BGM 打架。这给独立声音轨留下了干净的视频输入。若转码失败，代码会保留原始 MP4；合成时仍须主动去掉原始音轨。
- `backend/projects.py` 已持久化 Project 和 VideoTask，`merge_video_results` 按 Shot 取最新终止任务。`voice`、`music`、`render` 还是 `reserved`，`backend/v1_router.py` 的 `/audio`、`/render`、`/render/status` 只返回占位。前端目前停在 Storyboard 完成状态，没有试听或成片页面。
- `VideoTask.shots` 和合并结果没有实测视频时长、fps、画面尺寸、素材入点/出点。`Shot.duration_s` 同时充当生成时长和最终成片时长，难以修掉生成头尾的不稳定画面，也难以计算叠化重叠。
- `merge_video_results` 对每个 Shot 取最新终止结果；如果重生成失败，失败结果会遮住之前成功的视频。成片应保存明确选中的成功 `task_id`，并让用户可以回退到已有成功版本。

## 2. 核心结构：画面、旁白和音乐分别排在同一时间轴上

声音单元按自然语义句或段落建立，视频单元按可剪辑素材建立。两者通过绝对时间和 `narration_ids` 相连，不能用 `shot_id → 一段音频` 作主数据模型。

```json
{
  "edit_version": 1,
  "project_id": "p_xxx",
  "plan_version": 1,
  "reference_version": 1,
  "duration_ms": 15000,
  "video": [
    {"shot_id": 1, "task_id": "vt_a", "source_in_ms": 300,
     "source_out_ms": 6100, "timeline_start_ms": 0, "duration_ms": 5800,
     "transition_out": {"type": "cut", "duration_ms": 0}},
    {"shot_id": 2, "task_id": "vt_b", "source_in_ms": 200,
     "source_out_ms": 5400, "timeline_start_ms": 5800, "duration_ms": 5200,
     "transition_out": {"type": "cut", "duration_ms": 0}}
  ],
  "narration": [
    {"unit_id": "n01", "asset_id": "voice_n01", "text": "示例旁白。",
     "timeline_start_ms": 4500, "duration_ms": 4300, "speaker": "host"}
  ],
  "music": [{"asset_id": "bgm_01", "timeline_start_ms": 0,
             "source_in_ms": 0, "duration_ms": 15000}],
  "ambience": [],
  "captions": [{"unit_id": "n01", "start_ms": 4500, "end_ms": 8800,
                "text": "示例旁白。"}]
}
```

这里 `n01` 从 4.5 秒开始，到 8.8 秒结束；画面在 5.8 秒从 Shot 1 切到 Shot 2，但旁白不受切点影响。这是 Vlog 中常见的声音跨镜头，FFmpeg 上只是连续的旁白流叠在独立的视频流上。若一个 Seedance 源片内已有两个自然镜头，同一 `task_id` 也可以被两个剪辑单元用不同入/出点引用，不必维持永久的一 Shot 一视频文件限制。

独立轨道不等于只在最后按总时长机械叠加。每个旁白单元还需要 `visual_subjects`、`required_visual_range_ms` 与所覆盖 Shot 的 `narration_ids`。例如 6–10 秒念到荷花，就给荷花画面安排至少覆盖这一发声区间的时间槽；如果在 8 秒切镜，后一镜仍应是荷花或与该句直接相关的细节。程序校验时间窗覆盖，生成后再检查实际素材中荷花是否在所需片段可见；否则调整剪点、使用另一段素材或重生成，不能让已经离开画面的镜头硬配这句。

每次渲染只使用服务端已保存的 `task_id`/`asset_id` 和选中的成功视频；计划快照记录文案、参考图和素材版本。重新生成一个 Shot 只替换相关画面素材、重算转场并重新渲染；文案和旁白没有变化就不重做 TTS。若修改文字或语速，则重新测时并使旧 Storyboard/Render 失效。

## 3. 先定真实声音，再定分镜

1. 文案确认后先做“口播稿校验”：去掉标题/话题标签，按语义和换气点拆出稳定 `unit_id`，用目标时长估算密度；对明显超量的文案要求自动精简或用户编辑。不能把 266 字硬塞进 15 秒。
2. 对每个语义单元用同一音色、风格和语速合成 TTS；中长单元可覆盖多个 Shot。保存无损或高质量原始声音、实测时长和字/句时间戳。时间戳若 TTS 不提供，做强制对齐；字幕取真实发声时间，不取 `【0-15s】` 标记。
3. 试听并确认后，把 `narration_units`（时间、地点/事实引用、视觉要求）连同 `visual_profile` 输入 Storyboard。Storyboard 为每镜安排时间槽、所覆盖的旁白 ID、参考图 ID、视觉任务和前后镜头的剪辑关系。模型继续负责创意，程序负责总时长、重叠和实体/参考图一致性校验。
4. 旁白比目标稍短时，在句末和段落之间留自然呼吸、画面空镜及音乐尾奏；略长时优先精简措辞，少量变速只作微调。BGM 可以与 Shot 视频生成并行，声音测时必须先于正式分镜。

Storyboard 要分别给出 `generation_duration_s` 和成片使用的 `timeline_duration_ms`。例如生成 7 秒、实际用 5.5 秒，剩余画面可用于选剪点和转场；最终只用 2.5 秒的细节镜头也可以从 4 秒以上的生成素材中裁切。15 秒生成上限没有余量时，拆分时间槽或准备额外素材，不要依赖边界画面恰好可用。

第一版可暂不做字级强制对齐：至少保存每个语义句真实开始/结束，字幕逐句显示。后续需要卡点和逐字字幕时再细化。

## 4. 转场：剪辑规律比提示词更重要

独立生成的两个视频没有共同的最后一帧/第一帧条件，仅靠“相邻镜头丝滑衔接”提示词无法保证连续动作。现在所有 Shot 是独立提交和独立轮询，更是如此。建议按下列顺序实现：

| 场景 | 首选处理 | 原因 |
| --- | --- | --- |
| 同地标的远景→细节/人物→环境 | 直接切镜；保持色温、景别变化、主体方向与运动方向；挑合适的剪点 | Vlog 和宣传片本来就大量使用硬切，连续旁白/BGM 会让切镜自然 |
| 同一动作要连续、同一人物不能跳变 | 同一段 10–15 秒内生成多个镜头，或串行生成并用上一段参考视频/尾帧；在实际模型 API 与账号上逐项验证 | 此类关系需要视觉条件，仅凭文字难以锁定 |
| 时间、地点或情绪明显变化 | 0.2–0.5 秒叠化/音效桥接，或让音乐进入下一段；慎用叠化 | 叠化表达段落转移，对不同建筑/主体强行叠化会出现双影 |
| 生成片头/片尾有形变、卡顿、突兀音效 | 用实测入/出点剪掉，必要时降低运动重生成 | 固定整条生成片长不能保证可用区间 |

把全局风格（时间、色温、真实地点的稳定结构、画面比例、镜头方向）加入 Storyboard，并为相邻 Shot 输出 `continuity_group`、`transition_out`、动作/构图锚点。对承担实景真实性的建筑，不应为了“无缝”让模型幻想建筑背面或虚构桥接运动。生成后抽取相邻源素材尾/首帧与运动特征，必要时人工选剪点；色彩匹配和连续声音比给每个切点叠化更有收益。

Seedance 2.0 官方案例展示了多镜头生成和参考视频延长；这值得做第二阶段实验，但仓库目前 `ark_client.submit` 只发送文字与 `reference_image`，不能假定这个账号的当前模型允许某种首尾帧/视频参考参数组合。先用正式 API 文档和最小付费实验验证，再加串行生成模式。

### 4.1 串行生成：让后一镜真正看见前一镜

Seedance 2.0 官方说明支持视频、音频输入参考，也支持视频延长。对连续动作，优先验证“延长前一段”模式：上一镜的结尾是下一镜的真实条件，提示词指定接下来的动作与镜头变化。对同一地点的远景→细节镜头，则验证“参考前一段”模式：上一镜提供色温、人物、方向、运动和声音氛围，下一镜仍以当前 RAG 实景参考图和指定视觉主体为准。把上一镜只写进文字提示词，模型并没有实际看到它；普通参考也不保证下一镜第一帧与上一镜最后一帧几何无缝。

生成计划按 `continuity_group` 分组，组内 `shot_1 → shot_2 → shot_3` 串行提交，组与组之间可并行。每个 Shot 保存 `generation_mode`（独立/视频参考/视频延长）、`parent_shot_id`、`parent_task_id`、`reference_video_asset_id`、可选 `reference_audio_asset_id`、RAG 参考图 ID，以及输出任务 ID。下一镜必须等待上一镜成功、源视频下载且通过可用性检查后才能提交；上一镜失败时不应让后续镜头偷偷退化为独立生成。跨地点/时间/故事段落时开启新组，避免长期连锁把地标结构和人物细节带偏。

当前 `_run_video_jobs` 一次提交所有镜头后并行轮询，`ark_client.submit` 只有文本和图片输入；所以这个方案现在无法直接运行。客户端要增加经实际方舟 API 验证的视频/音频输入，调度器要按依赖提交并持久化等待/失败状态。上一镜生成的 URL 有有效期，需保留可再上传/引用的源文件。`_download_video` 目前在转码成功后删除原始 MP4，`transcode_web` 用 `-an` 剥离声音；若要把上一镜原生旁白或环境音作为后一镜的声音参考，必须先保存原音素材，同时另存无声网页预览版。不能用无声预览版声称已经给了“音频参考”。

声音参考可帮助后一镜沿用音色、节奏和环境氛围，但官方能力描述并不等于跨多个 4–15 秒生成任务能逐字念对同一首诗、锁定固定音色，或让半句话自然续接。要试 Seedance 原生解说，先让每组围绕完整语义句生成，提取源片音轨做听感/转写/时序检查；完整 BGM 仍应由成片 Composer 统一铺设，避免每镜单独生成一截音乐。若旁白准确性是硬要求，统一 TTS 旁白可以跨这些视频切点连续播放，并用实测时间窗保证荷花画面覆盖念到荷花的句子。前镜视频参考解决“画面彼此认识”，语音时间窗解决“旁白与画面认识”，两者都需要。

组内某镜重新生成后，引用其旧版本的后续 Shot 应标为失效并重新生成或重新确认，因为后续视频已经把旧镜内容当作条件。这样会增加等待和重生成成本；组间并行、只串联强连续段落可以控制影响。最小验证用两镜同一荷花场景，固定文案/参考图/时长，对比独立生成、参考前镜和延长前镜：检查接缝首尾帧、主体/真实地点一致性、原音音色及逐字准确率，再决定哪种模式用于生产。

### 4.2 关键帧、全局参考与一致性检查的文旅版

四层框架适配文旅视频，但约束的主次与人物连续短剧不同：景点真实身份和已确认实景参考是最高优先级，前镜生成画面只是辅助连续性证据。现有 `visual_profile` 已汇总景点真实结构、可变光线、受限机位和 `view_catalog`；`bind_storyboard_references` 按 Shot 选择景点参考图，`compile_shot_input` 向 Seedance 传原始实景图片。这可扩展为按 `place_id` 生效的地点级参考，而不是给全片所有地点强塞同一张“全局景点图”。若全片有固定主持人/游客，再增加经过确认的人物多视角参考与服装档案；纯风景片不需要凭空造一个固定人物。

Storyboard 除机位/景别/主体外，增加 `continuity_group`、`transition_intent`（连续动作/匹配切镜/换场）、`visual_anchor_ids`、所覆盖的 `narration_ids` 和必要的画面时间窗。每个连续组的状态记录 `place_id`、真实主体、拍摄时间/天气、镜头末端运动方向、人物服装/位置、上一镜选定的稳定关键帧、镜头剪点和不能出现的结构变化。不要把整个上一镜的描述无差别塞给下一镜；只传下一镜真正需要保持的状态。

关键帧从**选定成功版本的可用出点附近**提取，而不是直接取物体变形或卡顿的文件最后一帧。连续动作/跟拍优先尝试前镜源视频或关键帧的延长/首帧条件；普通远景→荷花特写只把前镜出点帧当作色温、岸线和运动方向的参考，第二镜的荷花实景特写图仍是地标与细节的主参考。若方舟当前接口只接受 `reference_image`，这张关键帧属于软参考，不能把它称作 API 已锁定的“下一镜首帧”；首帧/尾帧专用输入能力须单独查证和实测。不同景点、昼夜切换或语义新段落重置局部关键帧，保留全片画幅/调色/字幕/配乐等全局风格。

Visual Consistency Checking 分两级：**硬校验**检查景点身份、RAG `must_keep` 结构、受限机位/建筑新增、画面主体是否覆盖对应口播时间窗；**软校验**比较相邻选定出点/入点的构图、主色、曝光、运动方向、人物外观与服装。先过滤和重生成错误镜头，再选剪点、硬切或短转场；不能只凭像素差小就认定文旅画面正确，因为同一建筑的不同景别本来差异很大。由生成镜头提取的关键帧通过硬校验后才允许进入下一镜参考，防止错误被串行放大。

最小实现从同一景点的两镜开始：第一镜荷塘/岸线远景，第二镜荷花特写；对比仅有 Shot 实景图、实景图加前镜稳定出点帧、实景图加前镜视频参考。分别评价景点真实性、荷花口播时间窗覆盖、色温/运动连续性和接缝观感。验证有效后只在强连续组启用关键帧传递，避免让全片每个 Shot 都等待上一镜。

## 5. 配音、BGM 与自然环境声

- **旁白**：豆包语音合成模型 2.0 可作为首选试验。其 V3 TTS 是豆包语音产品的独立 `openspeech.bytedance.com` 接口，需该产品的 AppID、Access Token、音色/资源权限。2026-09-15 使用用户提供的 key 对火山方舟 `/api/v3/models` 查询成功，返回 132 个条目；筛选后有 Seedance 视频条目，没有语音/音乐条目。向方舟 `/api/v3/audio/speech` 发送空 JSON 探测得到 HTTP 404，没有触发合成。**这只能证明当前方舟路径与这个 key 不构成可用 TTS 接口；不能否定独立豆包语音服务。**
- **Seedance 原生声音**：字节官方说明 Seedance 2.0 可生成旁白/人物解说、台词、环境音和 BGM，并给出带旁白的生成示例。当前 `ark_client.submit` 只把视觉 Prompt 与参考图发给模型，未传入指定的语义句、统一音色或声音时间轴；`transcode_web` 又剥离所有声音。若以 Seedance 原生旁白作为正式配音，必须实测逐字准确率、专有名词发音、同一音色跨 Shot 一致性、句子起止时间和重新生成稳定性。它可以作为短片试验，但不能直接假定能承担整条 60 秒宣传片的唯一旁白轨。
- **固定音色边界**：此次能核实的 Seedance 官方说明是“可以参考输入音频中的声音元素并生成旁白”，没有找到当前方舟视频生成 API 可直接指定豆包 TTS `voice_type`/固定音色 ID 的依据。参考同一段人声可作为一致性试验，不能当成强约束。如果保留 Seedance 原生旁白，要先保存未剥离音轨的源文件，并在提示词中要求无 BGM；若模型仍把音乐与人声混成一条音轨，再叠全片 BGM 就会打架。与之相比，独立豆包 TTS 提供明确的固定音色参数。
- **BGM**：第一版使用有明确授权、可循环的曲库素材，选一首覆盖整片，在段落边界换曲而不是每镜换曲。字节另有“AI 音乐生成大模型”的生成纯音乐 API；官方快速接入指南要求企业认证、单独开通服务并用 AK/SK，当前方舟 key 不能直接代替。豆包产品页也列有 Doubao-Seed-Music，但此次方舟目录没有音乐条目，所以先不把音乐模型当作生产依赖。
- **环境声/SFX**：按地点与事件排布可复用的环境声床，例如水波、街道远声、脚步、钟声等；只在有画面依据时加入。环境声在切镜处做短淡变，必要时可先听到下一场景的声音（J-cut）或把上一场景的声拖过切点（L-cut）。当前转码会剥离 Seedance 原音，不能从成片用的 MP4 直接提取它的环境音。
- **混音**：旁白在前景；BGM 在有旁白时自动压低、无旁白处回升，增益变化做短斜坡；环境音更轻。最后限制峰值并统一响度，试听手机外放和耳机。TTS 段落之间保留换气/语义停顿，不在字词中间做 crossfade。

## 6. Composer 与接口落点

建议新增 `backend/pipeline/audio_client.py`（独立 TTS 适配器）、`audio_timeline.py`（语义单元/实测时长/字幕）、`composer.py`（FFmpeg 编排）。`AudioTask`、`RenderTask` 像 `VideoTask` 一样持久化，`Project.voice/music/render/final_video` 写入真实结果和版本快照。`/audio` 返回异步任务状态，`/render` 读取服务端持久化的剪辑计划，`/render/status` 返回最终 MP4 URL、预览 URL、时长和失败原因。`RenderRequest.shot_ids` 应使用整数 ID；任意外部 `voice_url`/`music_url` 不应成为服务端合成的权威输入，改为项目内 asset ID。

Composer 的确定性步骤：

1. 从视频任务历史选定每个 Shot 的成功版本，校验本地文件存在。再用 FFprobe 得到时长、fps、分辨率、像素比例和流信息；任务宣称 `completed` 但本地文件丢失时阻止渲染。`imageio-ffmpeg` 当前只保证 FFmpeg 可执行文件，FFprobe 需要另行确保可用或加入替代媒体探测实现。
2. 对源片 `trim/setpts`、缩放/裁切为统一规格、统一 fps/pix_fmt，并显式 `-an`；硬切用 concat，叠化用 `xfade` 并从总时间扣掉重叠时长。先生成低码率预览，再生成正式 MP4。
3. 按绝对时间放置旁白、音乐、环境声；旁白轨可跨任意数量切点。混音用 `adelay`/`amix`、音量自动化或 `sidechaincompress`，最后 `loudnorm`/限幅。
4. 根据实际语音时间写字幕（ASS/SRT），合成或外挂字幕；编码 H.264/yuv420p + AAC、`faststart`，并用 FFprobe 核实最终时长和 A/V 同步。保留计划 JSON 与源任务 ID，确保重新渲染可复现。

FFmpeg 官方滤镜文档支持 `trim`、`xfade`、`atrim`、`adelay`、`amix`、`acrossfade`、`loudnorm` 等实现。关键不是某条固定命令，而是先由剪辑计划计算精确时间与过渡重叠，再生成滤镜图。

## 7. 建议落地顺序

1. 修正口播字数预算和文案超量校验；实现 TTS 适配接口，先允许上传/选择本地旁白文件作闭环输入。用真实声音时长生成 `narration_units`，Storyboard 使用这些时间。
2. 做最小 Composer：三个真实 Shot、一个连续旁白、一个连续 BGM、逐句字幕；硬切优先。完成 15 秒样例全片并检查 2 个内部切点、字幕和响度。
3. 加剪辑入/出点、色彩匹配、短叠化、环境声和 J/L cut；重生成单 Shot 后自动失效并重渲染成片。
4. 验证 Seedance 多镜头单片/视频参考延长的实际接口能力，再为必须连续的段落启用串行生成。把视觉真实性检查纳入转场评价，不为了丝滑牺牲地标一致性。
